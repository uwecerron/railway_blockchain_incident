# Tracing the Railway wallet drainer with Covalent GoldRush

On **October 21, 2026** a breach at Railway exposed customer environment variables, and with them the private keys of hot wallets that apps kept in `.env` files. Within hours one address, `0xd9773325282874d18cb83f1fe50f14c39750b2ee`, started sweeping those wallets across every EVM chain it could reach ([Tay Monahan's thread](https://x.com/tayvano_/status/2113056813646238196) was the first public writeup).

This repo reconstructs the attack from on-chain data using the [Covalent GoldRush API](https://goldrush.dev): every chain the attacker touched, every victim wallet, every dollar priced, and where the money went. It is both a **forensic report** and a **tutorial** you can rerun on any address.

> Data window: 2026-10-21 00:00 UTC to 2026-10-22 ~16:30 UTC. All numbers below come from `out/REPORT.md`, generated by this code. The attacker address and every other address listed are public on-chain data.

The take is conservative on purpose. A transfer counts only when it can be priced honestly: native coins use the transaction's own USD quote, and tokens use GoldRush's historical daily price. **117 transfers of unpriced tokens are left out**, so the true figure is somewhat higher.

### What the signatures prove: the keys were stolen, not phished

Every transaction is classified by **who signed it**:

| Role | Txs | Meaning |
|---|---:|---|
| `victim_signed_native` | 408 | The **victim's own key** signed a native-coin transfer to the attacker |
| `victim_signed_token` | 209 | The **victim's own key** signed an ERC-20 `transfer()` to the attacker |
| `attacker_initiated` | 169 | The attacker's key: approvals, swaps, bridges, cash-out |
| `third_party_push` | 38 | Someone else pushed tokens in (spam, poisoning) |
| `other` | 36 | Mostly fake "attacker sent" events emitted by poisoning contracts |

617 transactions were signed by the victims' own keys. There was no `approve` + `transferFrom` pattern and no malicious contract, so this was not a drainer-kit phish. The attacker held the raw private keys, which fits secrets leaked from environment variables.

### How the sweeper behaved

- **It ran in parallel across chains.** 80 wallets were drained on more than one chain, up to 7 chains for a single wallet. The median gap between a wallet's first and last chain was about 30 minutes, and the long-tail chains fell within 3 minutes of each other.
- **It knew about DeFi protocols.** It took a victim's `syrupUSDC` (Maple) and filed a **Maple redemption request** for it, even though the position was worth $5 ([`0x1fd718…a292`](https://etherscan.io/tx/0x1fd718ed30c66463328d5300b3e6b400b54f059d8bf863adaaaca325b8d5a292)). It also moved Polymarket `pUSD` out through LI.FI and an order-based bridge.
- **It went after newer chains as well as the big ones.** Robinhood Chain had 46 victims and 55 drains between 22:24 and 22:45. MegaETH, Monad, Plasma, HyperEVM and Arc all appear in the activity list.
- **Losses were concentrated.** The top 4 wallets account for **$347,730 (91%)**. The other 227 wallets lost about $34K combined, much of it gas money and small balances that the script took anyway.

### Where the money went

Each send from the attacker to a plain address was followed hop by hop. Two custodial patterns showed up, both of which investigators know well:

- **Native deposit.** A fresh address receives ETH and forwards all of it within hours to a wallet with hundreds of thousands of transactions.
- **Token deposit.** An address receives USDT/USDC, a **gas-station wallet** tops it up with a little native coin, and then the tokens are swept to the same kind of high-volume wallet.

What this means for responders:

1. **Most of the money went to a small number of custodians.** On Arbitrum, three deposit addresses fed one hot wallet and two of them shared a gas station. On Ethereum, four deposit addresses fed one hot wallet and two shared a gas station. That is how a single service's deposit infrastructure looks, so a handful of compliance requests covers about $360K.
2. **Two of the Ethereum deposit addresses have been in use since 2020.** Custodians assign deposit addresses to customer accounts, so this points to established accounts rather than throwaway ones. The custodian can confirm.
3. **Tay attributed the cash-out to HitBTC.** The on-chain pattern fits a centralized exchange. This repo deliberately leaves the hot wallets unlabeled because a name is an attribution claim that GoldRush data alone cannot verify.
4. **There is still something to freeze.** The 999 USD₮ on Celo was unmoved when this was written, and Tether can freeze USD₮.

### The poisoners went after the attacker

Within minutes of each cash-out, address-poisoning bots deployed fake tokens such as `ꓴ឵ՏᎠ឵Ⲧ`, `UЅDC` (a hair space plus a Cyrillic Ѕ) and `USḌC`. Those tokens emitted **fake Transfer events saying the attacker had sent the same amount to a lookalike of the real deposit address**. The bots hoped the attacker would later copy the wrong address out of their own history. GoldRush shows **29 of these mirror events**, for example:

| Real deposit address | Lookalike planted in the attacker's history | Mirrored amount |
|---|---|---:|
| `0xf006355119…6e8e` | `0xf00601d42b…6e8e`, `0xf0061b38ae…6e8e` | 225,146.00 |
| `0xffc890fe09…f1cd` | `0xffc8614531…f1cd`, `0xffc8d02e4d…f1cd` | 40,043.78 |
| `0xaaa939dacf…901c` | `0xaaa2d423b0…901c` | 55,046.92 |
| `0xa3cce5eb44…c0a3` | `0xa3ccf822be…c0a3`, `0xa3cce18236…c0a3` | 15,186.71 |

Vanity twins of the **attacker's own address** (`0xd977b862…b2ee` and `0xd97995a8…b2ee`) also sent dust to the attacker's deposit address. These are not the attacker's sibling wallets, so anyone clustering by "who sent to the same deposit address" would get this wrong. The code flags them with a prefix/suffix lookalike check.

### What was excluded and why

- **19 inbound junk transfers** from 16 contracts: 13 lookalike-ticker spoofs and 6 scam airdrops with URLs in the name.
- **117 unpriced transfers**, mostly memecoins with no GoldRush price on the day.
- Large marks on illiquid tokens are capped at $250K per transfer. Native coins and the canonical USDC/USDT/WETH/WBTC/DAI contracts are trusted at any size, which is why the $256K USDT drain counts.

### Run the trace

Every stage is resumable and caches API responses on disk, so you can stop and continue at any point:

```bash
python3 -m railway_trace fetch     # which chains, then every tx on each   (~25 calls per busy chain)
python3 -m railway_trace price     # historical USD for every token touched
python3 -m railway_trace hops      # follow cash-outs to deposit + hot wallets
python3 -m railway_trace report    # write out/REPORT.md + CSVs
# or all at once:
python3 -m railway_trace all
# any address, any window:
python3 -m railway_trace all --address 0xYourSuspect --since 2026-10-01T00:00:00Z --out out_suspect
# long jobs in short sessions:
python3 -m railway_trace fetch --budget 120      # stops starting new chains after 120s; rerun to resume
```

## 3. Tutorial: the five GoldRush calls that do the work

**1. Which chains has this address touched?** One call covers 100+ chains:

```python
api.get(f"/v1/address/{addr}/activity/")
# items: {"name": "eth-mainnet", "chain_id": "1", "first_seen_at": ..., "last_seen_at": ...}
```

This is how the 22 chains were found, including Robinhood Chain, MegaETH, Plasma and Arc, which most explorer-based workflows would miss.

**2. Full history per chain, with decoded logs:**

```python
# page 0 is the OLDEST page. Walk links.next forward until it's null.
for page in itertools.count():
    data = api.get(f"/v1/{chain}/address/{addr}/transactions_v3/page/{page}/", {"quote-currency": "USD"})
    yield from data["items"]                      # each tx has value_quote, gas_quote_rate, decoded log_events
    if not data["links"]["next"]: break
```

> Gotcha we hit: if you start at page 0 and follow `links.prev`, you stop after 100 transactions without any error. That silently undercounted Ethereum and Base in our first run.

**3. Who signed is the whole story.** Classify each transaction by its signer: a victim's key sending to the attacker is a drain, and the attacker's key is routing (`railway_trace/classify.py`). Decoded `Transfer` events give you the ERC-20 legs, and the logs on the attacker's own transactions (`Swap`, `Approval`, `MessageSent`, `RedemptionRequested`) show which venues it used.

**4. Price honestly:**

```python
api.get(f"/v1/pricing/historical_by_addresses_v2/{chain}/USD/{c1},{c2},.../",
        {"from": "2026-10-14", "to": "2026-10-21"})   # take the latest close on or before the day
```

A missing price is useful information in itself, because freshly deployed lookalike tokens never have one. That plus a homoglyph check on the ticker removes every spoofed USDT/USDC.

**5. Follow the money:**

```python
api.get(f"/v1/{chain}/address/{a}/transactions_summary/")   # total_count: 4 vs 749,435 tells you everything
api.get(f"/v1/{chain}/address/{a}/transactions_v3/page/0/", {"no-logs": "true"})
api.get(f"/v1/{chain}/transaction_v2/{tx_hash}/")            # decoded logs for token sweeps
```

## 4. Code design

```
railway_trace/
  config.py        Secret type + key loading (env or .env). Nothing else.
  client.py        HTTP only: Bearer auth, retry/backoff on 429/5xx, error redaction, gzip response cache
  goldrush.py      One function per endpoint; knows response shapes, nothing about forensics
  classify.py      Pure: roles, movements, spoof detection, pricing rules
  forensics.py     Pure: victims, timeline, cadence, venues, cash-out, poisoning mirrors
  hops.py          Deposit-address and hot-wallet following (uses goldrush.py)
  labels.py        Tiny, conservative address book (only entries corroborated by events)
  report.py        Markdown/CSV output only
  cli.py           Wires the stages together; resumable with time budgets
  secrets_scan.py  Fails if anything key-shaped is present outside .env
tests/             30 offline tests: security, classification, pricing, forensics, pagination, hops
```

- **Single responsibility.** HTTP, endpoint shapes, analysis rules and output formatting are separate modules, so a change to one does not touch the others.
- **Dependency inversion.** Analysis code depends on a `Getter` protocol rather than `requests`. Tests pass in fakes, and you could swap in another data source the same way.
- **Pure core.** `classify` and `forensics` do no I/O, so every rule in this README has a unit test.

### How the API key is protected

- The key lives only in your environment or in `.env`, which is listed in `.gitignore`. `.env.example` contains no value.
- It is wrapped in a `Secret` type that cannot be printed, formatted, pickled or modified (`repr` gives `Secret(****)`).
- It is sent only in the `Authorization: Bearer` header and never in a URL or query string. `GoldRushClient` will not accept a plain string.
- Every error path (HTTP bodies, network exceptions, API error envelopes) passes through `Secret.redact()` before it is raised.
- The response cache is keyed by `sha256(path + params)`, and the key is never part of that input or of the stored data. There is a test for this.
- `python3 -m railway_trace scan-secrets` scans the repository and `out/`, including the gzip cache, for anything key-shaped. Run it before every commit, or as a pre-commit hook:

```bash
printf '#!/bin/sh\npython3 -m railway_trace scan-secrets\n' > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

## 5. Caveats

- USD values use GoldRush daily prices and the transactions' own quotes. Unpriced tokens are excluded, so the totals are a floor.
- "Victim" means a wallet whose key signed a transfer to the attacker during the window. A few could be the attacker's own funding wallets, so check `victims.csv` before contacting anyone.
- Custodian identification is based on behavior (deposit-address patterns and transaction counts) and is not a verified label.
- Prices for Oct 21 were not yet published when this was generated, so the code uses the most recent close in the previous seven days (Oct 20).
